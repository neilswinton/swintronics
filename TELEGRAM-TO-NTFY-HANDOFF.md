# Specification: Migrate all notifications from Telegram to ntfy.sh

**Audience:** This document is a complete work specification for an AI coding agent (or human)
working in the `swintronics` repo (`/home/neil/git/swintronics`). It assumes no prior context
beyond this document and the repo itself. Read the repo's `CLAUDE.md` before starting.

---

## 1. Goal and decisions (already made — do not re-litigate)

Replace Telegram as the cluster's notification channel with **hosted ntfy.sh**.

- **Provider:** `https://ntfy.sh` (hosted, free tier). The topic name is a long random secret
  generated by Terraform and stored in Infisical as `SERVER_NTFY_TOPIC`. Publishing is a plain
  `curl -d "message" https://ntfy.sh/<topic>`.
- **Abstraction:** no Apprise/ntfy container. Host-side sending is centralized into ONE helper
  script (`/usr/local/sbin/swintronics-notify`); Gatus keeps its native `ntfy` alerting provider.
  A future provider swap should touch only these two places.
- **Migration style:** two PRs with a burn-in period.
  - **PR 1** adds ntfy *alongside* Telegram everywhere (dual-send).
  - **Burn-in:** 1–2 weeks of real traffic.
  - **PR 2** removes Telegram entirely.

**Hard constraint:** the pre-reboot notification fires during early system shutdown, and the
boot notification fires before Docker services are up. The notification endpoint must therefore
be an **off-box plain-HTTPS service** reachable from host shell scripts. Hosted ntfy.sh
satisfies this. Never route these host notifications through a container on the same machine.

## 2. Current Telegram integration map (verified 2026-07-22)

Three channels. A and B share the Infisical secrets `SERVER_TELEGRAM_BOT_TOKEN` /
`SERVER_TELEGRAM_CHAT_ID` (canonical copies live in the Terraform Infisical project, folder
`/server`; `terraform/secrets.tf:124-131` copies everything in `/server` into the runtime
Infisical project at `/`, where Ansible reads them).

### Channel A — Gatus container (service uptime + backup alerts)

- `ansible/services/gatus/config.yaml.j2:10-13`:
  ```yaml
  alerting:
    telegram:
      token: ${GATUS_TELEGRAM_BOT_TOKEN}
      id: ${GATUS_TELEGRAM_CHAT_ID}
  ```
- Telegram is the **only** alerting provider. Roughly 12 endpoints (internal endpoints +
  `external-endpoints` for backups) each repeat an inline alert list like:
  `alerts: [{type: telegram, failure-threshold: 3, success-threshold: 1, send-on-resolved: true}]`
- `ansible/services/gatus/.env.j2:4-5` maps the secrets:
  ```
  GATUS_TELEGRAM_BOT_TOKEN={{ infisical_secrets.secrets.SERVER_TELEGRAM_BOT_TOKEN }}
  GATUS_TELEGRAM_CHAT_ID={{ infisical_secrets.secrets.SERVER_TELEGRAM_CHAT_ID }}
  ```
- Flow: Infisical runtime `/` → `playbooks/deploy-versions.yml` templates `.env.j2` → `.env` →
  container env → Gatus's native `${VAR}` substitution in `config.yaml`.

### Channel B — host scripts, outside Docker

All source `/etc/swintronics/monitoring.env` (root:root 0600, written by
`ansible/playbooks/configure-system-services.yml:99-110`, which currently contains
`TELEGRAM_BOT_TOKEN` and `TELEGRAM_CHAT_ID`) and curl `api.telegram.org` directly:

| Sender | Installed by / lives at | Telegram curl location |
|---|---|---|
| `swintronics-reboot-scheduled.sh` (fires when `/run/reboot-required` appears) | `configure-system-services.yml:117-186` | `:137-142` |
| `swintronics-pre-reboot.sh` (ExecStop hook, runs early in shutdown while network is up; uses `--max-time 5 --retry 1`) | `:190-238` | `:227-233` |
| post-boot failure alert (only if `swintronics-post-boot.service` fails) | `:319-323`, unit at `:340`, `:358` | `:319-323` |
| `swintronics-boot-notify.sh` (every boot, `After=network-online.target`) | `:384-448` | `:425-430` |
| `update-dockhand` (root cron; skips gracefully if monitoring.env absent) | `ansible/services/dockhand/update-dockhand` | `:47-56` |

`ansible/services/backup/backup.sh` does **not** talk to Telegram (it uses Gatus push
endpoints and healthchecks.io; alerting reaches the user via Gatus → Channel A).

### Channel C — in-app settings on the server (NOT in this repo; manual UI steps)

- **Beszel hub**: user notification settings (stored in
  `/docker-data/volumes/beszel/beszel_data/data.db`) contain a Shoutrrr webhook URL
  `telegram://<bot_token>@telegram?chats=<chat_id>`. Shoutrrr supports ntfy.
- **Dockhand**: notification config (stored in `/docker-data/volumes/dockhand/db/dockhand.db`)
  uses an Apprise URL `tgram://<bot_token>/<chat_id>`. Apprise supports ntfy.
- **Home Assistant**: confirmed NOT using Telegram. No work needed; docs should note that any
  future HA messaging integration should use ntfy with the same topic.

### Documentation referencing Telegram

`DEPLOYING.md`, `README.md`, `CLAUDE.md` (prerequisites list + `/server` secrets table),

## 3. PR 1 — Add ntfy alongside Telegram (dual-send burn-in)

Create a feature branch (repo rule: never commit to main; confirm with the user before
committing; commit + push together; PRs are squash-merged).

### 3.1 Terraform: generate the topic secret (`terraform/secrets.tf`)

- Add `random_password.ntfy_topic`: `length = 32`, `special = false` (ntfy topics allow
  `[A-Za-z0-9_-]`). Follow the existing `random_password.restic` pattern in this file.
- Add an `infisical_secret` resource writing it to the **runtime** project, folder `/`, key
  `SERVER_NTFY_TOPIC` (follow the existing runtime-secret resource patterns in this file).
- The ntfy server URL is not a secret — do not store it in Infisical. Consumers default to
  `https://ntfy.sh` (see below) so a future self-hosted server is a small config change.
- The user will read the topic value from the Infisical UI to subscribe on their phone; a
  sensitive Terraform output is optional.

### 3.2 Gatus (`ansible/services/gatus/`)

- `config.yaml.j2` — add an `ntfy` provider beside the existing `telegram` block:
  ```yaml
  alerting:
    ntfy:
      url: https://ntfy.sh
      topic: ${GATUS_NTFY_TOPIC}
      priority: 3
    telegram:
      token: ${GATUS_TELEGRAM_BOT_TOKEN}
      id: ${GATUS_TELEGRAM_CHAT_ID}
  ```
- **Centralize the alert lists**: define the repeated per-endpoint alert block once at the top
  of the template with Jinja2 (e.g. `{% set service_alerts %}...{% endset %}` or a macro) and
  reference it from every endpoint, replacing the ~12 hand-copied
  `alerts: [{type: telegram, ...}]` lists. During burn-in the shared block contains **both**
  `- type: ntfy` and `- type: telegram` entries (same thresholds:
  `failure-threshold: 3, success-threshold: 1, send-on-resolved: true`). Preserve any
  per-endpoint threshold deviations if found — check each endpoint before replacing.
  Verify the rendered YAML is valid (render locally or run
  `ansible-playbook playbooks/deploy-versions.yml --check --diff`).
- `.env.j2` — add: `GATUS_NTFY_TOPIC={{ infisical_secrets.secrets.SERVER_NTFY_TOPIC }}`

### 3.3 Shared notify helper (`ansible/playbooks/configure-system-services.yml`)

- Install a new script `/usr/local/sbin/swintronics-notify` using the same
  embedded-content/copy pattern as the existing scripts in this playbook. Behavior:
  ```bash
  #!/usr/bin/env bash
  # Usage: swintronics-notify "<message text>"
  # Sends to every provider configured in /etc/swintronics/monitoring.env.
  set -u
  [ -r /etc/swintronics/monitoring.env ] && . /etc/swintronics/monitoring.env
  msg="${1:?usage: swintronics-notify <message>}"
  ok=1
  if [ -n "${NTFY_TOPIC:-}" ]; then
      curl -s --max-time 5 --retry 1 -d "$msg" \
          "${NTFY_URL:-https://ntfy.sh}/${NTFY_TOPIC}" >/dev/null || ok=0
  fi
  if [ -n "${TELEGRAM_BOT_TOKEN:-}" ] && [ -n "${TELEGRAM_CHAT_ID:-}" ]; then
      curl -s -X POST --max-time 5 --retry 1 \
          "https://api.telegram.org/bot${TELEGRAM_BOT_TOKEN}/sendMessage" \
          -d "chat_id=${TELEGRAM_CHAT_ID}" \
          --data-urlencode "text=${msg}" >/dev/null || ok=0
  fi
  [ "$ok" -eq 1 ]
  ```
  Keep the total time budget tight (`--max-time 5 --retry 1`) — the pre-reboot caller runs in
  the shutdown window.
- Extend the `monitoring.env` template (`:99-110`) with `NTFY_URL=https://ntfy.sh` and
  `NTFY_TOPIC={{ infisical_secrets.secrets.SERVER_NTFY_TOPIC }}`; keep the `TELEGRAM_*` lines.
- Replace the four inline Telegram curl blocks (`:137-142`, `:227-233`, `:319-323`,
  `:425-430`) with calls to `/usr/local/sbin/swintronics-notify "<same message text>"`.
  Message text, emoji, and `$(hostname -s)` interpolation stay in the callers unchanged.
  Preserve each script's existing error tolerance (notification failure must never fail the
  surrounding unit).

### 3.4 Dockhand cron (`ansible/services/dockhand/update-dockhand`)

- Replace the curl block at `:47-56` with a guarded call:
  ```bash
  if [ -x /usr/local/sbin/swintronics-notify ]; then
      /usr/local/sbin/swintronics-notify "⬆️ $(hostname -s): dockhand updated ${old} → ${new}" \
          || echo "warning: notify failed"
  fi
  ```
  (Preserves current behavior of skipping silently on clusters without monitoring.)

### 3.5 Docs

- `DEPLOYING.md` / `README.md` / `CLAUDE.md`: describe ntfy alongside Telegram (state that
  Telegram is in a burn-in period and will be removed). Add the manual onboarding step:
  install the ntfy app (iOS/Android/web), subscribe to the topic in `SERVER_NTFY_TOPIC`
  (server `https://ntfy.sh`). Add `SERVER_NTFY_TOPIC` to the CLAUDE.md runtime-secrets table.
- Document Channel C explicitly: Beszel and Dockhand hold their own notification URLs in-app
  (UI paths in §3.6); future Home Assistant messaging should use ntfy with the same topic.
- `.claude/skills/add-service/SKILL.md` and `.claude/skills/deploy-and-verify/SKILL.md`:
  update Telegram mentions to reflect both channels.

### 3.6 Manual UI steps (user performs; include in PR description as a checklist)

- **Beszel** (Settings → Notifications): add a Shoutrrr ntfy URL for the same topic
  (verify exact scheme against current Beszel/Shoutrrr docs; typically
  `ntfy://ntfy.sh/<topic>`) alongside the existing Telegram webhook. Send a test notification.
- **Dockhand** (notification settings): add an Apprise ntfy URL
  (`ntfys://ntfy.sh/<topic>`) alongside the existing `tgram://` entry. Test it.

### 3.7 Deploy & verify (after PR 1 merges — repo rule: merged ≠ deployed)

1. `cd terraform && terraform apply` → creates `SERVER_NTFY_TOPIC` in the runtime project.
2. User subscribes to the topic in the ntfy app.
3. `cd ansible && source .env && ansible-playbook playbooks/configure-system-services.yml`
   → installs the helper, rewrites monitoring.env and the four host scripts.
4. Run the repo's `/deploy-and-verify gatus` skill (or
   `ansible-playbook playbooks/deploy-versions.yml`) → Gatus restarts with new alerting.
5. Smoke tests:
   - `sudo /usr/local/sbin/swintronics-notify "test from $(hostname -s)"` → arrives on
     **both** Telegram and ntfy.
   - Force a Gatus alert (e.g. stop a monitored container briefly) → both channels fire,
     then send the resolved notice.
   - Deliberate reboot → "shutting down" (pre-reboot) and boot notification arrive on both.
   - Beszel + Dockhand in-app test notifications arrive on ntfy.

### 3.8 Burn-in exit criteria (before starting PR 2)

1–2 weeks with: ≥1 organic or forced Gatus alert, ≥1 full reboot cycle, ≥1 dockhand update
(or forced run), and Beszel + Dockhand test notifications — all delivered on ntfy.

## 4. PR 2 — Remove Telegram

1. `gatus/config.yaml.j2`: delete the `telegram` provider block and the `- type: telegram`
   entry in the shared alerts block. `gatus/.env.j2`: delete both `GATUS_TELEGRAM_*` lines.
2. `configure-system-services.yml`: remove `TELEGRAM_*` from the monitoring.env template and
   the Telegram branch from `swintronics-notify`.
3. Secrets (manual + terraform): delete `SERVER_TELEGRAM_BOT_TOKEN` and
   `SERVER_TELEGRAM_CHAT_ID` from the **Terraform** Infisical project's `/server` folder in
   the Infisical UI, then `terraform apply` — the wholesale `/server`→runtime copy in
   `secrets.tf` removes them from the runtime project. No `.tf` code change expected.
4. In-app (manual): remove the Telegram webhook from Beszel and the `tgram://` URL from
   Dockhand, leaving only ntfy.
5. Docs/skills: remove all remaining Telegram references, including the CLAUDE.md `/server`
   secrets table rows and the "Telegram bot" prerequisite bullet.
6. Deploy: `configure-system-services.yml` + `/deploy-and-verify gatus`; rerun §3.7 smoke
   tests expecting ntfy-only delivery.
7. Last (manual, after everything verifies): revoke/delete the bot via BotFather.

## 5. Constraints and cautions for the executing agent

- **Never** put a locally-hosted container in the path of the host reboot/boot notifications
  (see hard constraint in §1).
- **Never** print or commit the live Telegram bot token / chat id; they exist only in
  Infisical and in root-owned files on the server.
- Repo workflow rules (from CLAUDE.md + user preferences): feature branch always; ask the
  user before committing; commit and push together; squash-merge via
  `gh pr merge <n> --squash --admin --delete-branch`; a merged playbook change is not done
  until it has been deployed and verified on the target.
- ntfy.sh free-tier notes: security = secrecy of the random topic name (acceptable here — no
  secrets in message bodies); daily message caps are far above this cluster's volume. If
  auth is ever wanted, self-hosted ntfy or a paid reserved topic drops into
  `NTFY_URL`/`NTFY_TOPIC` + Gatus `token:` without re-architecting.
